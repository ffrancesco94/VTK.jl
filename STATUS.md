# VTK.jl — Status & Implementation Plan

Last updated: 2026-11-25. Stage 0 correctness, scoped diagnostics, and
ownership hardening is **complete** on the `stage0-correctness` branch.
WrapIt migration **complete** and the legacy
hand-written CMake wrapper **removed** (2026-10-29). The WrapIt-generated +
shim-merged `libvtk_julia` now loads from `VTK_julia_jll` by default;
`VTKJL_LIB` remains available for local development builds. Branch/PR CI builds
the wrapper from each checkout on Julia 1.11–1.13; tag CI exercises the
published JLL. Time-dependent
(transient) EnSight/CGNS readers were added on 2026-11-24 (`src/temporal.jl`).
The Julian-PyVista gap audit, follow-up sequence (§7), and raw/high-level
capability matrix (`docs/src/capability_matrix.md`) were also added on
2026-11-24. Durable gotchas live in `AGENTS.md`.

## 1. Goal

Julia bindings for a CFD-oriented subset of VTK 9.7: data model, XML I/O, and
manipulation filters (clip, slice, cell↔point conversion, contour, surface
extraction). No rendering, no MPI-aware API. Long-term: a maintainable
binding-generation pipeline (WrapIt + shim) and an idiomatic "Julian" layer
on top of the raw bindings.

## 2. Current state (what works)

Binary/runtime foundations:

- `VTK_jll` 9.7.1 provides full headers, `lib/cmake/vtk-9.7` configs, and the
  `vtkWrap*` tools; we build our binding module against it. No local VTK
  build needed.
- Binding generation: the **default build is the WrapIt driver**
  (`gen/build_wrapper.jl` → `gen/wrapit/build.jl`): it builds **WrapIt from
  upstream source** ([`grasph/wrapit`](https://github.com/grasph/wrapit),
  including the macro-truncation and libclang-22 fixes — no `WrapIt_jll`),
  generates the CxxWrap bindings from VTK
  headers, merges the hand shim + auto-shim, and installs the result at
  `wrapper/build/libvtk_julia.so`. Requires git, CMake, a C++17 compiler,
  libclang + OpenSSL dev headers. Gotcha: the precompile cache does not
  track `VTKJL_LIB` — clear `~/.julia/compiled/v1.*/VTK` when switching.
- Generated surface: **72 classes registered, ~3,150 generated methods** +
  25 auto-shim methods (18 classes) + ~90 hand-shim methods, all in one
  library. The auto-shim (`gen/wrapit/auto_shim.jl` → `shim_auto.cpp`)
  derives owning `X_new` factories and macro accessors (`vtkSetMacro`,
  `vtkBooleanMacro`, …) from the VTK headers textually — these are invisible
  to libclang because they only exist after the C preprocessor runs; 282
  more were skipped because WrapIt already emitted them. A single generic
  `SetInputData`/`GetOutput` on `vtkAlgorithm` covers all
  readers/writers/filters (downcasts in the Julian layer), so adding a class
  usually needs no shim edits. Hand-written remainder (`shim_vtkjl.cpp`,
  ~460 lines): ownership policy, error window, zero-copy workers, downcasts,
  up-casts, convenience adapters.
- Self-healing clash vetoes: when the shim and WrapIt would register the same
  method, `veto_shim_clashes!()` mechanically adds the generated overload to
  `veto.txt` (11 hand-maintained lines + ~65 auto-derived) and regenerates
  until converged.
- Upstream engagement: WrapIt bug reports and validated fixes are now merged
  upstream, including Bug 1 ([issue #76](https://github.com/grasph/wrapit/issues/76))
  and libclang-22 support; the build uses upstream WrapIt directly.
- MPI: VTK_jll is an MPI-enabled build; `libmpi` (MPICH/OpenMPI/MPIABI
  flavor) is pre-loaded in `VTK.jl` before the wrapper library is dlopened.
- Ownership: all factories/outputs return `vtkSmartPointer{T}` registered via
  CxxWrap's custom smart-pointer traits (`IsSmartPointerType`,
  `ConstructorPointerType`). Specialized finalizers queue native wrappers
  without entering VTK; serial safe points drain automatically, while
  multithreaded/raw batches use explicit quiescent `drain_vtk_deletions` calls.

Wrapped surface (generated by the WrapIt driver + merged shim):

- `vtkDataArray` family: abstract API (components, tuples, names, resize),
  factories for Float32/Float64/Int32 plus a **generic typed factory**
  `data_array(T, ncomp)` covering all of VTK's scalar types via
  `vtkAbstractArray::CreateArray`, **zero-copy views** via
  `vtkArrayDispatch` → `GetVoidPointer` → CxxWrap `make_julia_array`
  (AOS-only, mirroring VTK's own buffer-protocol caveat). Views are created
  directly at the target dimensionality (flat vector or `(ncomp, ntuples)`
  matrix) as plain `Array`s; `create_if_not_exists<ArrayRef{V,2}>` is needed
  since CxxWrap pre-registers only 1-D array wrapper types.
- Data model: `vtkPoints`, `vtkUnstructuredGrid`, `vtkPolyData`,
  `vtkImageData` (types registered with true VTK inheritance; construction
  currently exposed for unstructured grids), field data (`vtkPointData`/
  `vtkCellData`) with `AddArray`/`GetArray`/`SetActiveScalars`.
- I/O: `vtkXML{UnstructuredGrid,PolyData,ImageData,RectilinearGrid,StructuredGrid}-
  {Reader,Writer}` (`.vtu/.vtp/.vti/.vtr/.vts`) plus `vtkXMLMultiBlockData-
  {Reader,Writer}` (`.vtm` containers with `block`/`set_block!`/`nblocks`);
  writers emit zlib-compressed appended data by default, or raw appended
  data (`raw_appended=true`) which ReadVTK.jl can parse.
- CFD readers: `vtkGenericEnSightReader` (`.case`, steady + transient —
  this is what the Julian layer drives), `vtkEnSightGoldReader`,
  `vtkCGNSReader` (`.cgns`), and `vtkXMLPPolyDataReader` (`.pvtp`
  parallel summaries); all produce `vtkMultiBlockDataSet` except
  `vtkXMLPPolyDataReader` which yields `vtkPolyData`. The hand shim adds
  `GenericEnSightReader_new`, a `GetTimeSteps` helper reading the
  `TIME_STEPS()` output-information key, and `DeepCopyDataObject` for
  detached snapshots; `UpdateInformation`/`UpdateTimeStep` come from the
  generated bindings.
- Legacy I/O: `vtkGenericDataObjectReader`/`vtkGenericDataObjectWriter`
  (`.vtk` format, any dataset type), plus specific
  `vtkDataSetReader`/`Writer`, `vtkUnstructuredGridReader`/`Writer`,
  `vtkPolyDataReader`/`Writer`, `vtkStructuredGridReader`/`Writer`,
  `vtkRectilinearGridReader`/`Writer` for type-specific access.
- Filters: `vtkTableBasedClipDataSet`, `vtkCutter`, `vtkCellDataToPointData`,
  `vtkPointDataToCellData`, `vtkContourFilter`, `vtkDataSetSurfaceFilter`,
  plus `vtkPlane` implicit function.
- Type hierarchy mirrors VTK inheritance (`vtkUnstructuredGrid <: vtkPointSet
  <: vtkDataSet <: vtkDataObject`) enabling Julia-side up-cast conversions of
  smart pointers and `SafeDownCast`-based downcasts (`UnstructuredGrid(obj)`,
  `PolyData(obj)`, `ImageData(obj)`).
- Error handling: high-level readers, filters, temporal updates, and writers
  use per-operation `vtkCommand` observers with severity, native status, and
  algorithm/file context. Warnings are nonfatal, actual failures throw
  `VTKError`, and raw generated calls remain deliberately unchecked.

Julian layer (`src/dataarray.jl`, `src/typedarray.jl`, `src/dataset.jl`,
`src/cells.jl`, `src/filters.jl`, `src/temporal.jl`):

- `data(da)`/`raw_data(da)`: zero-copy `(ncomp, ntuples)` / flat views
  derived from an **owning** `VTKDataArray` wrapper ("wrapper-owns-
  everything"): the underlying array stays alive as long as any derived
  view does, even if the original handle is dropped.
- `VTKDataArray{T}`: parametric `AbstractMatrix{T}` of shape
  `(ncomp, ntuples)` holding the smart pointer (ownership), zero-copy cached
  view, typed `getindex`/`setindex!`, `resize!`; `field_array`/`points_array`
  return typed wrappers or `nothing`.
- Grid construction: `Points()`, `UnstructuredGrid()`, `pts[i] = (x,y,z)`,
  `insert_cell!` (accepts raw ids or `VTKCellTypes.VTKCellType`),
  `set_points!`, `allocate!`; `UnstructuredGrid(points, cells)` from a 3×n
  matrix + `MeshCell` vector.
- `read_vtu`/`read_vtp`/`read_vti`/`read_vtr`/`read_vts`,
  `write_vtu`/`write_vtp`/`write_vti`/`write_vtr`/`write_vts`, `field_array`,
  `point_data`, `cell_data`, `activate_point_data!`.
- CFD readers: `read_ensight` (EnSight Gold `.case`),
  `read_cgns` (CGNS `.cgns`), `read_pvtp` (parallel PVTK `.pvtp`).
- Temporal readers (`src/temporal.jl`): `EnSightReader(path)` /
  `CGNSReader(path)` return a `VTKTemporalReader` wrapping the algorithm
  with its `timesteps`; `length`, `read_timestep(reader, i)` (1-based,
  any order), `read_at(reader, t; atol, rtol, copy)`, and `eachstep`.
  Results are detached deep copies by default; `copy = false` explicitly
  selects mutable pipeline-backed output. Timestep metadata is isolated from
  callers and collected `eachstep` results remain valid.
  `read_ensight`/`read_cgns` are one-shot reads of the reader's
  current output through the same layer.
- Legacy I/O: `read_legacy_vtk` (any `.vtk` dataset type, returns downcast),
  `write_legacy_vtk` (any dataset, format chosen automatically).
- Hierarchy-aware `downcast(obj)`: exact class-name dispatch plus `IsA`
  fallback for derived VTK classes. Unregistered data objects return owning
  generic `vtkDataObject` handles; null and incompatible forced downcasts throw
  deliberate VTK-specific errors.
- Cell/point access: `cell_type`/`cell`/`cells`/`eachcell` (VTKBase
  `MeshCell`, 1-based connectivity), `eachpoint`, `coordinates` (zero-copy
  typed 3×n view). Cell vocabulary comes from VTKBase (`VTKCellTypes`), the
  shared registry of ReadVTK/WriteVTK — `cells(grid)` is directly consumable
  by `WriteVTK.vtk_grid`.
- `plane`, `clip`, `slice`, `cell_to_point`, `point_to_cell`, `contour`,
  `extract_surface`, `calculator`, `gradient`, `threshold`, `stream_tracer`,
  `particle_tracer`, `line_source`, `sample_over_line`, `update!` — filters
  generated by `@vtk_filter` or hand-written for multi-input cases.

## 3. Test suite (455 tests serial, 457 with multithread/GC stress; all passing)

- **Array core**: typed creation, zero-copy write-through both directions,
  multi-component reshape, names, Int32 element type, GC churn with
  survivors.
- **Typed wrapper**: type-stable indexing, value round-trips through the
  typed API, zero-copy visibility, resize invalidation, type mismatches
  rejected, discovery from untyped factories.
- **Cells/iterators/converters**: VTKBase registry ids and names, 1-based
  connectivity, `eachcell`/`eachpoint`/`coordinates`, round-trip
  `UnstructuredGrid(coordinates, cells)` reconstruction, WriteVTK writes our
  mesh description and our reader reads it back.
- **Views vs GC**: views obtained via `data`/`raw_data` survive collection
  of the owner (wrapper, array, or entire grid) — dropping the last owner
  reference is safe under aggressive `GC.gc()` churn, through the untyped
  API, the typed wrapper, and grid field arrays.
- **Analytic oracles**: clip of unit hex against plane x+y+z=1 (inside-out)
  yields exactly the tetrahedron (1 cell, 4 points, max coordinate sum 1.0);
  default clip side verified as complement; constant-field c2p stays
  constant; linear-field p2c averages to 1.5 on a unit hex; slice at x=0.5
  gives the unit square; contour points lie on the isosurface; surface
  extraction preserves the 8 vertices; stream tracing a constant vector field
  through the unit hex produces an 11-point streamline.
- **Independent oracles**: our `.vtu` output verified with ReadVTK.jl (pure
  Julia); our reader verifies WriteVTK.jl output — both directions.
- **Robustness**: GC/finalizer stress across full pipelines; missing field
  names return `nothing`.
- **Auto-shim**: macro accessors
  (`InsideOutOn/Off`, `GetInsideOut`, `GetUseValueAsOffset`, `GetFileName`)
  and auto factories (`PolyData_new`).
- **Structured XML I/O**: `.vti/.vtr/.vts`
  round-trips through VTK.jl's own readers/writers, with WriteVTK.jl output
  read by VTK.jl and VTK.jl output re-read by VTK.jl (ReadVTK.jl does not
  parse zlib-compressed appended data, so the write-side oracle is limited
  to geometry/header checks); generic `downcast` dispatch on reader outputs.
- **CFD readers**: EnSight Gold `.case` with
  analytic oracle (unit hex); CGNS static case (file generated in-test
  with cgnslib via `CGNS_jll`) with coordinate/field oracles + missing-file
  error; parallel `.pvtp` summary + piece files written
  by WriteVTK, read back and verified.
- **Transient CFD readers**: transient EnSight Gold and CGNS cases —
  `timesteps`/`length`, out-of-order `read_timestep` with analytic field
  oracles, `read_at` lookup plus `ArgumentError`/`BoundsError` cases, and
  `copy = true` snapshots that survive later reader updates; steady EnSight
  (no steps) and static CGNS (single step) as temporal-reader inputs.
- **Legacy VTK I/O**: unstructured grid
  round-trip with field data (unit hex + temperature); missing-file error.
- **Stage 0 correctness**: scoped severity/status diagnostics, raw/stale message
  isolation, writer/reader context, null versus valid empty outputs, derived and
  unknown downcasts, nonnumeric arrays, facade nonmutation, scalar probing,
  connectivity/arity/bounds validation, multiblock lifetimes, aliased array-view
  resynchronization, detached `eachstep` retention, and concurrent pipelines
  with GC pressure. The full suite is also run with four Julia threads and two
  GC threads.

## 4. Known limitations / design debt

1. **Array interface**: zero-copy views are ownership-safe — `data`/`raw_data`
   return views derived from an OWNING `VTKDataArray` wrapper (the
   "wrapper-owns-everything" design), so the owner handle may be dropped.
   No C++ VTK destruction runs directly on GC finalizer threads: specialized
   smart-pointer finalizers enqueue wrappers for safe deferred deletion.
   Serial high-level entry points drain automatically; multithreaded/raw users
   establish quiescent drain points. `VTKDataArray` wrappers detect
   structural changes made through aliases/raw calls and resynchronize their
   cached matrix. Remaining caveats: previously extracted views are invalidated
   by VTK reallocation, and the grown region is NOT zero-initialized.
2. **Argument-passing pattern**: C++ methods take raw `T*`. The generated
   Julian overloads in `src/generated_methods.jl` accept smart pointers and
   forward via `_cp(T, obj)` (`CxxPtr{T}(obj[])`), so normal callers do not
   write the conversion. CxxWrap's by-value smart-pointer argument path is
   unusable for custom smart pointers (`Type{Dereferenced{T}}` dispatch is
   impossible — Julia's `Type` is invariant). Raw-pointer overloads remain
   available for low-level code.
3. **Arrays**: no typed get/set accessors (all access goes through zero-copy
   views or the slow double-based virtual API); SOA/variant arrays
   unsupported for zero-copy (guarded, throws).
4. **I/O**: XML + CFD formats (EnSight Gold, CGNS — both steady and
   transient via `UpdateTimeStep`, parallel `.pvtp`) +
   legacy `.vtk`; `.pvtu` is unwrapped. Writers only emit
   appended data for XML (fine for CFD); legacy writer emits ASCII.
   ReadVTK.jl (the pure-Julia oracle) does not parse zlib-compressed
   appended blocks, so compressed output is verified by re-reading with
   VTK.jl itself. Transient reads are detached snapshots by default;
   `copy = false` explicitly requests borrowed pipeline output.
5. **Data model**: unstructured grids fully constructible from Julia; other
   grid types readable but not constructible. Cell types are bare integers
   (`VTK_HEXAHEDRON = 12`).
6. **Downcasts**: generic name-based `downcast(obj)` dispatches through
   `DOWNCAST_REGISTRY`, built automatically at module load from the types
   the loaded library registers + their `downcast_foo` shim bindings — no
   manual registry edit when adding a grid type (add the type + shim
   binding, rebuild; only extend `DOWNCAST_SOURCES` for a genuinely new
   kind of type). Derived classes are resolved through `IsA`; unregistered
   classes return an owning generic handle rather than raising `KeyError`.
7. **Distribution**: `VTK_julia_jll` provides the wrapper on supported
   64-bit non-Windows platforms. Other platforms require a local C++17
   toolchain and the `VTKJL_LIB` override.
8. **WrapIt upstream**: Bug 1 and the libclang-22 macro-generation issues are
   fixed upstream. Bugs 2–4 remain worked around in the driver (AOS
   post-processor, `export_blacklist`, ostream vetoes).
9. **Particle tracer**: `Experimental.particle_tracer` is explicitly
   quarantined and its seed input is a VTK algorithm, not the `PolyData`
   returned by `line_source`. A static-grid
   smoke test crashed inside `vtkParticleTracerBase::Execute`; transient
   *reader* pipelines are now tested (EnSight/CGNS, 2026-11-24), but no tracer
   execution example is advertised until a temporal *filter* pipeline works.

## 5. Risks

- CxxWrap still schedules its `delete` finalizers on GC finalizer threads, but
  the specialized VTK implementation only enqueues wrappers. Actual deletion
  requires a quiescent point: automatic at serial high-level entry points and
  explicit with `force=true` for multithreaded/raw batches. Forcing a drain
  while another VTK call is active violates that contract and remains unsafe.
- Local regeneration builds upstream WrapIt from source and therefore needs
  network access and a working libclang toolchain. `VTKJL_WRAPIT_REF` can select
  a release tag for reproducibility; `VTKJL_WRAPIT_UPDATE=1` advances an existing
  checkout. Branch/PR CI therefore installs the native toolchain and builds the
  wrapper; tag CI uses the prebuilt JLL instead.
- VTK_jll has no Windows build; Windows support requires our own VTK build.
- VTK_jll's MPI flavor complicates end-user installs; escape hatch is a
  custom non-MPI VTK build (defer until requested).

threads plus two GC threads pass; generated-library integration and the
documentation build also pass.

### Stage 1 — coherent Julian facade over existing raw functionality

**Goal:** obtain the largest usability improvement without major new C++
surface. Raw factories and methods already exist for much of this work.

- [ ] Establish a clear stable high-level API versus raw generated API. Use
      Julian functions, multiple dispatch, array/dictionary/iteration
      interfaces, and selective public names rather than copying Python's
      method-heavy API verbatim.
- [ ] Add dictionary-like point/cell/general field access, array association
      lookup, active scalars/vectors/tensors/normals/texture coordinates,
      informative `show` summaries, and common metadata (`bounds`, `center`,
      dimensions, extents, origin, spacing, and array ranges).
- [ ] Build ergonomic constructors on top of the existing raw factories:
      PolyData points + verts/lines/polys/strips; ImageData dimensions/origin/
      spacing/direction; `RectilinearGrid(x, y, z)`; StructuredGrid coordinates
      + dimensions. Add bulk, precision-preserving UnstructuredGrid construction
      and safe buffer-adoption/copy constructors with explicit ownership.
- [ ] Add extension-dispatching read/save and configurable reader/writer
      objects. Expose the raw XML ASCII/binary/appended/compression controls
      uniformly and add a high-level legacy-binary option. Let other packages
      register formats without modifying VTK.jl.
- [ ] Systematically expose options already present on calculator, gradient,
      contour, threshold, cutter, and tracers: association/component selection,
      vector and coordinate variables, divergence/vorticity/Q-criterion,
      pass-through controls, integration parameters, and output naming.
- [ ] Add a safe persistent algorithm/pipeline abstraction over existing input
      connections and output ports: multiple inputs/outputs, parameter changes,
      re-execution, mixed dataset/algorithm inputs, progress, and cancellation.
      Keep eager one-shot filters as conveniences over this layer.
- [ ] Add named/recursive multiblock access and safe common temporal iteration.
      Establish a tested raw/high-level capability matrix and make examples
      executable so the supported API is distinguishable from generated surface.

**Exit criterion:** read → inspect → construct → attach fields → filter → save
workflows need no raw `_cp` calls, and ownership/copy behavior is predictable.

### Stage 2 — native Julia plotting with Makie

**Goal:** provide plotting through the Julia ecosystem rather than making
native VTK rendering the first implementation path. Plotting should be an
optional package extension so the core package does not acquire a graphics
backend or display-server requirement.

- [ ] **Build GeometryBasics interoperability first.** This is the practical
      prerequisite for the initial Makie recipes, not full Meshes.jl support.
      Define conversions for points, lines, and polygon/triangle faces plus
      point/cell field arrays. Document copy versus zero-copy behavior and keep
      VTK owners alive for any borrowed representation.
- [ ] Define geometry normalization before plotting: PolyData can map directly
      to points/lines/faces; volumetric unstructured grids need surface
      extraction and, where necessary, triangulation/tessellation; ImageData
      should map to image/volume plots with origin/spacing preserved; composite
      data needs recursive traversal. Do not silently discard cells that the
      initial GeometryBasics representation cannot express.
- [ ] Add Makie recipes/extensions for scalar-colored surfaces and wireframes,
      points/lines, vector/glyph display, ImageData volumes, and multiblock
      scenes. Support point/cell association, active-array selection, color
      maps and limits, opacity, colorbars, axes, labels, and camera controls.
- [ ] Use appropriate optional backends for static output, interactive windows,
      and notebooks. Add off-screen/headless CI and screenshot/regression tests
      from the beginning. Add simple profile plots for line-probe results.
- [ ] **Add Meshes.jl interoperability as a complementary bridge**, with an
      explicit target-representation policy for mixed-cell grids. It is useful
      for geometry operations and ecosystem exchange, but is not a strict
      prerequisite for a first Makie recipe if GeometryBasics conversion exists.
- [ ] Keep Tables.jl and StaticArrays adapters lightweight and optional where
      possible. Native VTK rendering wrappers remain deferred; reconsider them
      only for required features that Makie cannot provide, such as specific
      VTK picking/interactor or volume-rendering workflows.

**Exit criterion:** a user can plot the supported dataset types with fields,
save a screenshot in headless CI, and opt into interactive/notebook backends
without loading Makie in non-plotting workflows.

### Stage 3 — core sources and filter vocabulary

**Goal:** cover common PyVista-style workflows with individually tested,
Julian operations rather than pursuing class-count parity.

- [ ] Sources: sphere, box/cube, plane, cylinder, cone, arrow, point cloud, and
      structured/image sources.
- [ ] Geometry: transforms, outline, feature/all edges, triangulate,
      clean/merge coincident points, append/merge, connectivity/largest region,
      and point/cell subset extraction.
- [ ] Surface processing: normals, smoothing, decimation, subdivision, shrink,
      extrusion, tubes/glyphs, and hole cleanup according to user demand.
- [ ] Analysis: cell centers, cell sizes/quality, area/volume/length,
      integration, elevation, warp, interpolation, nearest-point/cell queries,
      and additional derivative quantities.
- [ ] CFD: complete tracer configuration and validated temporal particle paths.
- [ ] Every addition needs a high-level wrapper, ownership/error tests, an
      analytic or independent numerical oracle, relevant composite behavior,
      user documentation, and a capability-matrix update.

### Stage 4 — I/O, temporal/composite, tabular, and ecosystem breadth

**Goal:** complete workflow families and interchange with the wider Julia and
scientific-data ecosystems.

- [ ] Complete parallel XML readers/writers (`.pvtu`, `.pvti`, `.pvtr`,
      `.pvts`) and add `.pvd`/file-series collections. Distinguish serial piece
      merging from actual distributed MPI execution.
- [ ] Add STL/PLY/OBJ for surface interchange; prioritize XDMF/VTKHDF, Exodus,
      OpenFOAM, Fluent, Gmsh, and CFD writers according to demonstrated demand.
- [ ] Generalize temporal readers/writers and filters beyond EnSight/CGNS, with
      lazy field selection and safe snapshot semantics.
- [ ] Add named/metadata-rich composite trees, partitioned datasets,
      PartitionedDataSetCollection, and DataAssembly; defer AMR/hyper-tree grids
      until there is a concrete use case.
- [ ] **Wrap tabular data: `vtkTable` and `vtkTableAlgorithm`.** This records
      the requested "`vtkTableData`" work under the actual VTK 9.7 class name;
      the installed VTK headers contain `vtkTable` but no `vtkTableData`. Add
      the supporting array classes needed by real tables (notably string/
      variant arrays) and high-level Julia column construction/access. This is
      needed for native VTK table datasets, tabular I/O/filters, probe/chart
      workflows, and complete Tables.jl round trips. A Tables.jl adapter for
      existing point/cell fields can still land earlier without `vtkTable`.
- [ ] Finish GeometryBasics/Meshes.jl round trips, Tables.jl, StaticArrays,
      FileIO, and structured-axis/image integrations as package extensions.
      Preserve field data and metadata where the target representation permits.

### Stage 5 — distributed parallelism, advanced robustness, and platforms

**Goal:** address capabilities beyond the initial single-process Julian
PyVista core.

- [ ] Add MPI.jl communicator/controller integration, rank-aware piece/extent
      requests, ghost exchange, distributed filters, partitioning, and parallel
      writers. Test multiple ranks and more than one MPI flavor.
- [ ] Expand artifact/source-build CI beyond Ubuntu x64 to supported macOS and
      Linux-aarch64 targets; make local wrapper discovery use platform-specific
      library names and remove hard-coded MPI assumptions from integration tests.
- [ ] Define a deliberate Windows/VTK binary strategy. Add runtime wrapper
      capability/version checks and a reproducible local-library selection
      mechanism so stale precompile caches cannot silently select an
      incompatible generated method table.
- [ ] Add sanitizer lanes, large-data/64-bit/invalid-input tests, allocation and
      memory benchmarks, and unexpected-auto-veto/capability checks so generated
      coverage does not silently erode. Explore device arrays only after the
      host ownership model is settled.

### Ongoing documentation, testing, and release work (every stage)

- [ ] Maintain `docs/src/capability_matrix.md` alongside each feature change.
      Mark raw-only features explicitly and do not equate class registration
      with a supported high-level capability.
- [ ] Enable executable doctests for supported examples, repair stale extending
      and zero-copy guidance, strengthen structured/PolyData/keyword/error-path
      tests, and add end-to-end examples and a plotting gallery.
- [ ] Keep General registration and ordinary tagged installation as release
      goals once the Stage 0/1 public API baseline is coherent. Keep the
      wrapper/JLL compatibility checks and release CI green at every stage.
